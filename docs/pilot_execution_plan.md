# Pilot Execution Plan

**Status of the thing being piloted: PROTOTYPE VALIDATED — NOT PRODUCTION
READY.** This document turns [`docs/pilot_plan.md`](pilot_plan.md) (the
pilot's *objective*, users, scope, and success-metric categories) into an
*executable* plan: what gets measured, against what baseline, with what
dataset, in what session, judged by what decision framework. It does not
replace `pilot_plan.md` — it is what `pilot_plan.md` asked for next.

**We are not trying to prove production readiness here.** Production
readiness is a separate, already-scoped question answered by
[`docs/production_reference_architecture.md`](production_reference_architecture.md).
The open question this pilot answers is narrower and more valuable right
now: **does a shared, purpose-governed Context Layer actually create value
for the people who would use it** — before spending effort hardening
infrastructure for a product-market fit that hasn't been checked yet.

## 2. Pilot scope (unchanged from `pilot_plan.md`, restated for reference)

Two use cases against the **same shared Context Layer** — the point of
the pilot is to test reuse, so it deliberately does not introduce a third,
unrelated use case:

1. **Commercial HCP Intelligence** — HCP Engagement Agent
   (`agents/hcp_engagement.yaml`, `commercial_engagement` purpose).
2. **Clinical Site Intelligence** — Site Selection Agent
   (`agents/site_selection.yaml`, `site_selection` purpose).

Stretch goal, not required for a GO decision: publish a third agent
against the already-policy-defined-but-unpublished `medical_inquiry`
purpose (`context_layer/policy/engine.py` already has a
`PURPOSE_POLICIES["medical_inquiry"]` entry; no `agents/*.yaml` uses it
yet). If a pilot session has time and a stakeholder for it, onboarding
this third purpose live is itself evidence for the reuse hypothesis
(§4.1).

Data: synthetic, generated by `context_layer/data/synthetic_gen.py` —
**not** live production HCP data, per `pilot_plan.md`'s explicit scope
boundary.

## 4. Pilot hypotheses (new — makes `pilot_plan.md`'s objective falsifiable)

Each hypothesis names what would make it **true** and what would make it
**false**, so a pilot session produces a verdict, not just an impression.

### 4.1 Reuse hypothesis

> A shared Context Layer can serve two distinct agent use cases by
> publishing a new `agents/*.yaml` config, with zero changes to graph,
> policy, or retrieval code.

- **Supports:** both existing agents already satisfy this (no core code
  was written per-agent); a stretch third agent (`medical_inquiry`)
  published during the pilot with config only, no core changes, is
  additional live evidence.
- **Refutes:** a real pilot use case that turns out to need a code change
  to `context_layer/graph/`, `policy/`, or `retrieval/` — not just a new
  YAML file — to be served correctly.
- **Measured by:** `docs/pilot_metrics.md` §Product.

### 4.2 Context relevance hypothesis

> The context a stakeholder's agent retrieves is judged relevant and
> sufficient for their actual workflow (not just policy-compliant).

- **Supports:** business users rate retrieved context as useful in
  `docs/pilot_feedback_questions.md`; on the pilot scenario dataset
  (`evaluation/pilot_dataset/`), retrieved context matches the documented
  `expected_context_characteristics` for the scenario's purpose.
- **Refutes:** stakeholders report the context is technically
  policy-compliant but not what they'd actually need (e.g., missing a
  data point their real workflow depends on that the synthetic model
  doesn't capture).
- **Measured by:** `docs/pilot_metrics.md` §Quality + qualitative feedback.

### 4.3 Governance trust hypothesis

> Governance/compliance stakeholders judge the purpose-bound,
> bridge-whitelisted access model as mapping cleanly onto real
> organizational governance requirements — not just this prototype's own
> synthetic test cases.

- **Supports:** zero policy/bridge violations across organic pilot usage
  (not just the adversarial test suite, which was written by the same
  people who built the system); governance stakeholder explicitly
  affirms the bridge whitelist table (`graph/bridges.py`) reflects real
  rules in their feedback session.
- **Refutes:** a governance stakeholder identifies a real rule the
  current 3-purpose, 2-bridge model doesn't express, or any non-zero
  violation count during organic (non-adversarial) pilot usage.
- **Measured by:** `docs/pilot_metrics.md` §Governance.

### 4.4 Platform value hypothesis

> The AI Platform Owner judges this as reducing effort relative to each
> team building its own retrieval/governance stack per agent.

- **Supports:** platform owner rates onboarding effort as lower than
  their counterfactual (building retrieval + access control per agent)
  in `docs/pilot_feedback_questions.md`.
- **Refutes:** platform owner judges the abstraction not worth the added
  layer for their real integration surface.
- **Measured by:** `docs/pilot_metrics.md` §Product + qualitative feedback.

## 5. Measurement gaps (explicit, not papered over)

What this pilot *cannot* measure, and why, stated up front rather than
discovered mid-pilot:

- **No real usage volume yet.** All "now" metrics in `docs/pilot_metrics.md`
  are single-developer, synthetic-data, adversarial-and-happy-path test
  runs — not organic multi-user traffic. Adoption, error rate, and
  availability are genuinely unmeasured until the pilot runs.
- **No real LLM-graded answer quality yet.** RAGAS/DeepEval/LLM-judge have
  never run against a live model in this environment (no API key in the
  build/test sandbox) — `evaluation_reports/manual_llm_judge_pass.json`
  is one manually-performed pass, not a corpus. The pilot is the first
  chance to run these for real, if a provider key is supplied.
- **No real compliance sign-off.** The bridge whitelist
  (`graph/bridges.py`) encodes assumptions from the original design doc,
  not a reviewed real policy. Governance trust (§4.3) is exactly the
  hypothesis that tests this — it is not assumed true going in.
- **No production-scale performance data.** `docs/test_report.md` §7's
  numbers are single-process, in-memory, 50-HCP scale — informative as a
  prototype baseline, not predictive of production latency.

## 6. What this pilot deliberately does not attempt

Same boundary as `docs/pilot_plan.md`'s "Out of scope" — restated because
it bears directly on what NOW/NEXT/LATER prioritization (§`docs/roadmap.md`)
should and shouldn't include before pilot evidence exists: no production
infrastructure hardening, no real source-system connectors, no IAM/SSO
integration, no enterprise rollout. **The next unknown is product fit, not
production infrastructure** — see `docs/roadmap.md`.
