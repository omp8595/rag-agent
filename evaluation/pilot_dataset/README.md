# Pilot Evaluation Dataset

`scenarios.json` — 11 scenarios a pilot facilitator runs live during a
pilot session (`docs/pilot_workflow.md`), against the real Context Layer,
with a human comparing actual output to what's documented here.

## Why this lives outside `context_layer/evaluation/`

`context_layer/evaluation/datasets.py` (`build_evaluation_cases()`) is a
**runtime** dataset — the automated evaluation runner
(`context_layer.evaluation.runner`) imports it, executes each case, and
scores it automatically as part of CI and the deterministic test suite.

This dataset is explicitly **not** that. Per the pilot plan's own
constraint: *"Do NOT place the expected answer directly into the runtime
system. The dataset is for evaluation only."* Nothing under
`context_layer/` imports `evaluation/pilot_dataset/`, and
`scripts/run_pilot_scenarios.py` never feeds `expected_context_characteristics`
or `expected_policy_outcome` into the system under test — it only prints
them next to the system's real output, for a person to judge. The
separate top-level `evaluation/` directory (distinct from
`context_layer/evaluation/`) makes that boundary visible in the repo
layout, not just in a docstring.

## Scenario schema

Each entry in `scenarios.json`:

| Field | Meaning |
|---|---|
| `scenario_id` | Stable identifier, prefixed `N` (normal), `E` (edge), `A` (adversarial) |
| `type` | `normal` \| `edge` \| `adversarial` |
| `agent` | Which published agent (`agents/*.yaml`) runs this, or `null` for a policy-engine-level scenario not reachable through any published agent |
| `bound_purpose` | The purpose that agent is bound to (or, for `A1`, the unregistered purpose being tested) |
| `entity_id` | Which synthetic HCP (see `context_layer/data/synthetic_gen.py`) |
| `question` | The free-text question asked — per the design's own invariant, this never affects retrieval scope, only relevance ranking |
| `expected_allowed_domains` / `expected_forbidden_domains` | What the policy engine should and should not permit |
| `expected_context_characteristics` | A description of what a correct Context Package should contain — **not** a literal expected answer string |
| `expected_policy_outcome` | One of: `allow`, `allow_with_constraint`, `allow_empty`, `allow_no_leak`, `allow_but_question_text_has_no_effect_on_scope`, `error_not_found`, `deny_fail_closed`, `reject_422_extra_field` |

## Construction

Built from the same synthetic fixtures every other test in this
repository uses (`data/synthetic/`, generated by
`context_layer.data.synthetic_gen`), reusing real entity IDs already
established elsewhere in the codebase as meaningful examples:

- `HCP-001` — an HCP with no investigator record (a "normal" commercial
  case, and useful as a clinical-domain edge case: E3).
- `HCP-021` — the one active clinical investigator whose data touches
  both bridges at once (`docs/test_report.md`'s primary acceptance
  scenario reuses this same entity for exactly that reason).
- `HCP-031` — a former (inactive) investigator, used for N4 to prove the
  clinical domain still works correctly for a closed study assignment,
  not just the one always-tested active case.

12 scenarios: 4 normal, 3 edge, 5 adversarial (deliberately biased toward
edge/adversarial relative to a typical smoke-test set, since the point of
a pilot dataset is to give stakeholders — especially the governance
stakeholder — something harder than the happy path to watch fail
correctly).

## Running it

```bash
./.venv/bin/python scripts/run_pilot_scenarios.py                  # all 11
./.venv/bin/python scripts/run_pilot_scenarios.py --type adversarial
```

Prints each scenario's expected characteristics next to what the live
system actually returned. Grading is by eye, by the pilot facilitator and
stakeholder in the room — this script does not compute a pass/fail
verdict, on purpose.
